# GlassStream — Project Plan

## Project Goal

I am an individual developer building **GlassStream** for Meta Ray-Ban Display glasses using the **Meta Wearables Device Access Toolkit (DAT) for Android**.

The goal of the first version is deliberately simple:

> **Get data from the glasses into my Android application, and send data back to the glasses.**

I am **not building the ML system yet**. I first want to prove that I can establish a reliable bidirectional connection with the glasses and control the relevant input/output channels.

The desired eventual data flow is:

```text
                 META RAY-BAN DISPLAY
                         │
              ┌──────────┼──────────┐
              │          │          │
           Camera       Mic      Sensors
              │          │
              ▼          ▼
          ┌──────────────────────┐
          │    Android App       │
          │      GlassStream     │
          └──────────┬───────────┘
                     │
              processing/model
                     │
              ┌──────┴──────┐
              ▼             ▼
           Audio         Display
              │             │
              └──────┬──────┘
                     ▼
                 GLASSES
```

# 1. What We Are Actually Trying to Prove

The first milestone is **not AI**.

We want to prove these four things independently.

## A. Camera Input

```text
Glasses camera
      ↓
Meta DAT
      ↓
Android app
      ↓
Receive video frames
```

The Android app should be able to receive frames from the glasses' camera.

Eventually those frames will become input to the model:

```text
Camera
   ↓
Video frames
   ↓
ML model
   ↓
Prediction
```

Initially, we can simply display/log/process the frames to prove that streaming works.

---

## B. Audio Input

Eventually:

```text
Glasses microphone
        ↓
Android
        ↓
Audio stream/data
        ↓
Processing/model
```

The initial goal is simply to establish that audio from the glasses can reach the Android side.

---

## C. Audio Output

Once input works:

```text
Android
   ↓
generated audio
   ↓
glasses
   ↓
speakers
```

For the first test, we do not need an AI model.

We can generate something simple such as:

```text
"Hello from GlassStream"
```

and verify that the sound reaches the glasses.

Later:

```text
ML result
    ↓
Text
    ↓
TTS
    ↓
Audio
    ↓
Glasses speakers
```

---

## D. Display Output

Because these are **Ray-Ban Meta Display glasses**, we also want:

```text
Android
   ↓
DAT Display API
   ↓
Glasses display
```

Initially, the simplest possible test is something like:

```text
GlassStream

CONNECTED
```

Then:

```text
Object detected

PERSON
92%
```

Eventually the display can show information generated by the model.

# 2. Final Architecture

The eventual architecture should look approximately like this:

```text
                         ┌─────────────────────┐
                         │  Ray-Ban Display    │
                         │                     │
                         │ Camera              │
                         │ Microphone           │
                         │ Speakers             │
                         │ Display              │
                         └──────────┬──────────┘
                                    │
                           Meta Wearables DAT
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │     Android         │
                         │     GlassStream     │
                         │                     │
                         │ Device connection   │
                         │ Video receiver      │
                         │ Audio receiver       │
                         │ Audio transmitter   │
                         │ Display controller  │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Processing / Model  │
                         │                     │
                         │ CV / AI / logic     │
                         └──────────┬──────────┘
                                    │
                        ┌───────────┴───────────┐
                        ▼                       ▼
                     TTS/audio              Display data
                        │                       │
                        └───────────┬───────────┘
                                    ▼
                              Meta glasses
```

The Android phone is initially the **bridge and compute device**.

The glasses provide the hardware interfaces.

The Android application controls the communication and processing.

The ML model can be introduced later without changing the fundamental glasses connection architecture.

# 4. What We Are Doing Next

We should proceed in small, testable stages.

## Stage 1 — Android/DAT Configuration

Configure:

```text
AndroidManifest.xml
        ↓
DAT metadata
        ↓
Bluetooth permissions
        ↓
Internet permissions
        ↓
Meta registration callback
```

Then initialize the DAT SDK inside GlassStream.

We should not add camera/display code until the basic configuration works.

---

# 5. Stage 2 — Register GlassStream with Meta AI

The Android application needs to register with the Meta AI app.

Conceptually:

```text
GlassStream
     │
     │ "I want to connect"
     ▼
Meta AI app
     │
     │ registration
     ▼
Meta glasses
```

The application will use the DAT registration flow and monitor whether registration succeeds.

The Meta AI app remains part of the pairing/registration process.

- PyTorch

- cloud API

depending on what the project requires.

# 14. Stage 11 — Optimize the System

Only after functionality works do we investigate:

## Latency

```text
camera
 ↓
frame
 ↓
processing
 ↓
model
 ↓
output
```

Measure the time between these stages.

## Throughput

Determine how many frames per second can actually be processed.

## Resolution

Determine how much camera data is necessary.

## Model Speed

Determine whether the phone can run the model.

## Network Dependence

Determine whether inference should run:

```text
phone only
```

or:

```text
phone → cloud → phone
```

## Battery

Continuous camera streaming and inference can be expensive.

## Reliability

Test what happens when:

- Bluetooth disconnects
- glasses sleep
- phone loses network
- Meta AI disconnects
- camera stream stops
- model crashes

These are later engineering problems.

---

# 15. What We Are Deliberately NOT Doing Yet

For now, avoid:

- ML model
- Python backend
- cloud inference
- YOLO
- PyTorch
- speech recognition
- complex UI
- production signing
- Play Store
- release distribution
- optimization

The current objective is much narrower:

```text
GLASSES
   ↓
GET DATA
   ↓
ANDROID
   ↓
SEND DATA BACK
   ↓
GLASSES
```

Once that works, the AI layer is simply another processing component in the middle.
